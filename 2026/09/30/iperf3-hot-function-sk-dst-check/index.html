sk_dst_check引发的iperf3性能衰退

1. 问题场景

使用 iperf3 做 UDP 性能压测时：

  • 单核 CPU 可以发送出大约 2.7 Gbps 的 UDP 报文。
  • 使用 -P4 后，单核性能不足 2.4 Gbps，整体只有 9.44 Gbps，约有 10% 的衰退。
  • 使用 -P16 后，单核性能不足 1.3 Gbps，整体只有 19.8 Gbps，约有 50% 的衰退，问题严重。

注：CPU数量足够, 64核单NUMA

2. 问题结论

2.1. 结论

多核性能瓶颈：per-CPU 的 dst 路由缓存被多个线程跨 CPU 争抢，引用计数（atomic/rcuref）的原子操作限制了线性扩展；4 核以上线性增长明显下跌。

2.1.1. 触发条件

  • -P 参数会创建多个 UDP socket。
  • 这些 socket 都在 iperf3 运行的 CPU 上执行了 UDP connect。
  • 之后创建多个线程，每个线程使用一个 UDP socket 发包。

2.1.2. 简要分析

  1. UDP connect 后，内核会根据路由表的查找结果，缓存路由项 nhc（dst_entry）。
  2. 这个路由缓存是 per-CPU 的，因此缓存在 iperf 所在的 CPU A 上。
  3. 多线程创建完成后，内核会自动调度，将线程放到 CPU B 上运行；而 CPU B 上使用的 UDP socket 仍引用的是 CPU A 上缓存的路由结果。
  4. 结果：多个线程使用多个 UDP socket，却都使用了 CPU A 上缓存的路由结果。
  5. 因此每个报文发送时，内核调用 sk_dst_check，造成多 CPU 之间争抢路由引用计数的 atomic 操作。

sk_dst_check 及配套函数：

  1. UDP 发包时，发送前通过 sk_dst_check 检查缓存的路由 nhc。
  2. UDP 发包时，每包查询路由，并对缓存的路由引用做 atomic 操作。
  3. 多进程发送时 atomic 加一，发送后 atomic 减一，从而触发性能瓶颈。
  4. 6.4 版本已做过优化，使用 rcuref_get 降低 ref 的代价，但性能仍有待提高。

2.1.3. 临时规避

使用 ip 命令清理掉缓存的路由结果，强制 socket 重新查找路由。

这样可以避免 16 个 CPU 争抢同一个缓存的问题。但由于各线程会在多个核之间被来回调度，会出现以下情况：当前 CPU 上重新查找完路由后，会使用本 CPU 的缓存；一旦线程被调度到其他 CPU 上，仍会使用上一轮 CPU 的缓存。该方案并不完美，但可以规避这一危害。

3. 详细测试

3.1. 测试环境

  • 内核：Linux 6.6（无多路径路由、无策略路由/规则、未涉及 netfilter/conntrack）
  • iperf3：iperf 3.21（cJSON 1.7.15，compiled with pthreads support）

3.2. 对比测试

3.2.1. 单线程发送 UDP

  1. 测试命令：iperf3 -u -c 1.1.1.37 -b 4G -t 120
  2. 性能：2.7 Gbps 稳定，RX 侧 0 丢包。
  3. client 端：SI 消耗单核 CPU 的 35%，iperf3 消耗 100%。
  4. server 端：SI 消耗单核 CPU 的 17%，iperf3 消耗 35%，未到瓶颈。

3.2.2. 16 线程发送（-P16）

  1. 性能在 20 Gbps 左右，有抖动。
  2. client 侧发送 CPU 100%，SI 有冲突，最高接近 50%，不是瓶颈。
    • sk_dst_check：9.29%，占比继续上升。
    • dst_release：5.68%
  3. server 侧：SI 最高 70%+，分散比 TX 侧队列稍好（9 个队列）。

3.2.3. 热点函数：sk_dst_check

4.1. udp connect

4.5. 内核优化
